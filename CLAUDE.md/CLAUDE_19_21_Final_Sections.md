# 19. Quality Checklist

## Purpose

This checklist must be completed before any task is considered finished.

Quality is verified through objective review rather than assumption.

---

# Implementation Checklist

Confirm that:

- Requirements are fully implemented.
- Acceptance criteria are satisfied.
- Existing functionality remains intact.
- No duplicate logic has been introduced.
- Architecture has been respected.
- Code is readable and maintainable.
- Appropriate error handling exists.
- Configuration remains environment-driven.
- Documentation is synchronized where required.

---

# Technical Checklist

Verify where applicable:

- Project builds successfully.
- Linting passes.
- Formatting is consistent.
- Type checking passes.
- Imports are clean.
- No unused code remains.
- Dependencies are justified.

---

# Repository Checklist

Ensure:

- File placement follows project structure.
- Naming conventions are consistent.
- Related documentation is updated.
- Task progress accurately reflects implementation.

---

# Final Quality Rule

Never sacrifice long-term maintainability for short-term convenience.

Quality is a release requirement, not an optional improvement.

---

# 20. Definition of Done

A task is considered complete only when ALL of the following are true.

## Functional

- Requirements implemented.
- Acceptance criteria satisfied.

## Technical

- Code reviewed.
- Verification completed.
- No obvious regressions introduced.

## Architectural

- Architecture preserved.
- Existing abstractions reused where appropriate.
- No unnecessary duplication.

## Documentation

- Documentation updated where necessary.
- Task status reflects reality.

## Delivery

Every completed task should include:

- Summary
- Files created
- Files modified
- Verification performed
- Remaining risks (if any)
- Recommended next task

If any requirement above is missing, the task is not complete.

---

# 21. Appendix

## Engineering Priorities

When making decisions, prioritize:

1. Correctness
2. Architecture
3. Maintainability
4. Readability
5. Simplicity
6. Performance

---

## Engineering Motto

Understand first.

Design second.

Implement third.

Verify fourth.

Document continuously.

---

## Repository Principles

- Keep responsibilities separated.
- Prefer reuse over duplication.
- Preserve architectural consistency.
- Keep documentation synchronized.
- Improve the repository with every change.

---

## Final Operating Principle

Act as the long-term Lead Software Engineer for CodeSense AI.

Every decision should move the project toward a production-ready software platform while preserving quality, consistency, maintainability, and engineering discipline.

The repository is the primary source of truth.

The architecture is to be respected.

The roadmap defines implementation order.

Documentation and implementation must remain synchronized.

When sufficient information exists, continue independently.

When critical information is missing, pause, explain the issue, and request clarification.
